Part 6: Episode Lifecycle

Spawn & Reset Logic (Code)

How reset_robot_to_fixed_spawn teleports the car back to the starting line — with raycasting, quaternion math, and domain randomization hooks ready for the future.

What Happens When an Episode Resets?

Every time the car crashes, stalls, or crosses a boundary line, Isaac Lab calls the reset event for that environment. The function reset_robot_to_fixed_spawn is the single reset handler for the entire ARCPro RL system. It must:

📍

1. Pick a Spawn Point

Choose an (x, y) position on the track — currently a fixed location, but with domain randomization slots ready.

📡

2. Raycast for Ground Height

Fire a PhysX ray downward to find the actual road surface height at that (x, y), then place the car slightly above it.

🧭

3. Set Orientation & Velocity

Compose a quaternion for the spawn heading, optionally give the car an initial forward velocity.

🔄

4. Zero Everything & Reset FSMs

Write joint states to defaults, zero the distance accumulator, and reset the GoSignalManager FSM for the affected environments.

Let's walk through every single line.

Function Signature

EVENTS.PY 
def reset_robot_to_fixed_spawn(env, env_ids, asset_cfg=SceneEntityCfg("robot")):
    asset = env.scene[asset_cfg.name]
    num_resets = len(env_ids)
PLAIN ENGLISH

env — the full Isaac Lab environment object, which owns the scene, device, extras dict, etc.

env_ids — a 1-D tensor of which parallel environments need to be reset this step. If environments 3, 7, and 12 just died, this tensor is [3, 7, 12].

asset_cfg — tells the function which scene entity to reset. Defaults to "robot", which resolves to the Ackermann car asset registered in the scene config.

asset — the actual articulation object (rigid body + joints). We'll write poses, velocities, and joint states to this object.

num_resets — how many environments we're resetting. Every tensor we build below has this as its batch dimension.

⚡
Why env_ids and Not All Envs?

Isaac Lab runs thousands of environments in parallel. On any given step, only some of them might terminate. Resetting only the terminated environments (identified by env_ids) avoids disturbing the others mid-episode. This is the standard Isaac Lab reset pattern — every reset function receives the subset of environment indices that need work.

Domain Randomization Slots (Currently Disabled)

EVENTS.PY 
    base_spawn_x, base_spawn_y = -16.197, 5.50
    base_spawn_yaw = 1.5708

    rand_offset_x = torch.zeros(num_resets, device=env.device)
    rand_yaw = torch.zeros(num_resets, device=env.device)
    rand_vel_x = torch.zeros(num_resets, device=env.device)
PLAIN ENGLISH

base_spawn_x = -16.197, base_spawn_y = 5.50 — the fixed spawn coordinates in the track's local frame. These place the car at a specific point on the road (near the start line).

base_spawn_yaw = 1.5708 — that's $\frac{\pi}{2}$ radians, meaning the car faces in the +Y direction at spawn. The track is oriented so that the initial straight runs along the Y axis.

rand_offset_x = zeros — a placeholder for lateral randomization. If you wanted to randomly shift the spawn position left or right across the lane, you'd replace this with something like torch.uniform(-0.3, 0.3).

rand_yaw = zeros — a placeholder for heading randomization. You could add ±5° of random yaw perturbation to make the policy more robust to initial misalignment.

rand_vel_x = zeros — a placeholder for initial velocity randomization. In a domain-randomized curriculum, you might spawn the car already moving at 0.5–2.0 m/s to train the policy to handle rolling starts.

All three are zeroed out right now — the car always spawns at exactly the same position, heading, and velocity. But the infrastructure is in place to turn on randomization with a single line change each.

🎲
Domain Randomization — Why Bother?

In sim-to-real transfer, you want the policy to be robust to things it can't perfectly predict — its exact starting position, its initial heading, whether it's already moving. By randomizing these during training, the policy learns to handle a distribution of initial conditions rather than memorizing a single scenario. The current code has the scaffolding ready; you just need to swap the zeros for distributions when you're ready to increase training difficulty.

Computing the Spawn Position

EVENTS.PY 
    env_origins = env.scene.env_origins[env_ids]

    final_pos = torch.zeros((num_resets, 3), device=env.device)
    final_pos[:, 0] = env_origins[:, 0] + base_spawn_x + rand_offset_x
    final_pos[:, 1] = env_origins[:, 1] + base_spawn_y
    final_pos[:, 2] = env_origins[:, 2] + 0.12
PLAIN ENGLISH

env_origins — Isaac Lab tiles parallel environments across the simulation world. Environment 0 might be at (0, 0, 0), environment 1 at (100, 0, 0), etc. The env_origins tensor holds the world-space offset of each environment's origin.

We index with [env_ids] to get only the origins for the environments we're resetting.

final_pos[:, 0] — X position = environment origin X + base spawn X + random lateral offset (currently 0).

final_pos[:, 1] — Y position = environment origin Y + base spawn Y. No randomization on Y (the "forward" direction at spawn).

final_pos[:, 2] — Z position = environment origin Z + 0.12 meters. This is the safe drop height — we start 12 cm above the origin as a fallback, in case the raycast (below) fails to find the ground.

📐
Why 0.12 m?

The car's chassis sits roughly 5–8 cm above the ground when resting on its wheels. Setting the initial Z to 12 cm means the car will "drop" a few centimeters onto the surface — close enough that it lands gently within a few physics steps, but high enough that it doesn't clip through the road mesh. If the raycast below succeeds, this fallback value gets overwritten with a more precise height.

PhysX Raycasting — Finding the Road Surface

EVENTS.PY 
    quats = torch.zeros((num_resets, 4), device=env.device)
    query = omni.physx.get_physx_scene_query_interface()

    for i, env_id in enumerate(env_ids):
        world_x, world_y = final_pos[i, 0].item(), final_pos[i, 1].item()
        hit = query.raycast_closest(
            (world_x, world_y, 100.0),  # origin: high above the track
            (0.0, 0.0, -1.0),              # direction: straight down
            200.0                           # max distance: 200 meters
        )
PLAIN ENGLISH

quats — pre-allocate a (num_resets × 4) tensor for the spawn orientations. We'll fill these inside the loop.

query — the PhysX Scene Query Interface. This is NVIDIA's low-level physics engine API exposed through Omniverse. It lets us cast rays against the collision geometry of the entire scene.

The loop iterates over each environment being reset. We need to loop because raycast_closest is a CPU-side, single-ray API — it doesn't support batched GPU raycasts.

world_x, world_y — we extract the world-space X and Y coordinates (as Python floats via .item()) for this environment's spawn point.

raycast_closest fires a single ray from (world_x, world_y, 100.0) — that's 100 meters up in the air — straight downward (0, 0, -1), with a maximum travel distance of 200 meters. It returns the closest collision mesh hit along that ray.

This is how we find the actual elevation of the road surface at the spawn point, even if the track has elevation changes, banked curves, or is on uneven terrain.

📡
Why Not Use a Flat Z?

If the track were perfectly flat, you could hardcode z = 0.12 and be done. But real race tracks have elevation changes — hills, dips, banked corners. The raycast dynamically finds the road surface height at each spawn point, making the reset function work on any track geometry without manual tuning. The 0.12 m fallback only kicks in if the raycast misses (e.g., if the spawn point is off the road mesh).

Quaternion Composition for Spawn Orientation

EVENTS.PY 
        yaw_offset = rand_yaw[i].item()
        half_yaw = (base_spawn_yaw + yaw_offset) / 2.0

        quats[i, 0] = math.cos(half_yaw)  # w
        quats[i, 1] = 0.0                # x
        quats[i, 2] = 0.0                # y
        quats[i, 3] = math.sin(half_yaw)  # z
PLAIN ENGLISH

yaw_offset — the random heading perturbation for this environment (currently always 0.0).

half_yaw — quaternions use half-angle encoding. To represent a rotation of angle $\theta$ around an axis, the quaternion uses $\cos(\theta/2)$ and $\sin(\theta/2)$.

For a pure yaw rotation (around the Z axis), the quaternion is:

$q = (\cos\frac{\theta}{2},\ 0,\ 0,\ \sin\frac{\theta}{2})$

where the format is $(w, x, y, z)$. The X and Y components are zero because we're only rotating around Z (no roll, no pitch).

With base_spawn_yaw = 1.5708 ($\frac{\pi}{2}$) and zero offset, we get: half_yaw = π/4, so $w = \cos(\pi/4) \approx 0.707$ and $z = \sin(\pi/4) \approx 0.707$. This is the quaternion for a 90° turn — facing the +Y direction.

🧮
Quaternion Half-Angle Formula

A rotation of angle $\theta$ around the unit axis $\hat{n} = (n_x, n_y, n_z)$ is represented by the quaternion:

$q = \left(\cos\frac{\theta}{2},\; n_x \sin\frac{\theta}{2},\; n_y \sin\frac{\theta}{2},\; n_z \sin\frac{\theta}{2}\right)$

For a yaw-only rotation, $\hat{n} = (0, 0, 1)$ (the Z axis), so $q_x = 0$, $q_y = 0$, and only $q_w$ and $q_z$ are nonzero. This is the simplest possible quaternion — just the half-angle cosine and sine.

Snapping Z to the Road Surface

EVENTS.PY 
        if hit["hit"]:
            spawn_z = hit["position"][2] + 0.12
            final_pos[i, 2] = spawn_z
PLAIN ENGLISH

hit["hit"] — a boolean. True if the ray hit any collision geometry (the road surface), False if it sailed through empty space.

hit["position"][2] — the Z coordinate of the point where the ray hit the road surface. This is the exact ground elevation at this (x, y) point.

+ 0.12 — add the safe drop height (12 cm) above the ground surface. This ensures the car spawns slightly above the road and settles onto it in the first few physics steps, rather than spawning inside the mesh.

If the raycast misses (no road geometry at this point), the fallback Z from earlier (env_origins[:, 2] + 0.12) is kept. This is a defensive coding pattern — the function works even if the track mesh is missing or the spawn point is slightly off the road.

Initial Velocity in the World Frame

EVENTS.PY 
    velocities = torch.zeros((num_resets, 6), device=env.device)
    velocities[:, 0] = rand_vel_x * torch.cos(base_spawn_yaw + rand_yaw)
    velocities[:, 1] = rand_vel_x * torch.sin(base_spawn_yaw + rand_yaw)
PLAIN ENGLISH

velocities — a (num_resets × 6) tensor. The first 3 columns are linear velocity $(v_x, v_y, v_z)$ in the world frame, and the last 3 are angular velocity $(\omega_x, \omega_y, \omega_z)$. All start at zero.

velocities[:, 0] — world-frame $V_x = V \cdot \cos(\text{yaw})$. This projects the forward speed into the world X direction based on the spawn heading.

velocities[:, 1] — world-frame $V_y = V \cdot \sin(\text{yaw})$. Same projection into the world Y direction.

Since rand_vel_x is currently all zeros, the car always spawns stationary. But if you set rand_vel_x to, say, torch.uniform(0.5, 2.0), the car would spawn already moving forward at 0.5–2.0 m/s, correctly decomposed into world-frame X and Y components based on its heading.

The Z velocity, and all angular velocities, remain zero — no vertical launch, no spinning.

🧭
Body Frame vs. World Frame

rand_vel_x is conceptually the car's forward speed (body frame). But write_root_velocity_to_sim expects world-frame velocities. The $\cos/\sin$ projection converts:

$V_x^{\text{world}} = V_{\text{forward}} \cdot \cos(\psi), \quad V_y^{\text{world}} = V_{\text{forward}} \cdot \sin(\psi)$

where $\psi$ is the spawn yaw angle. This is the standard 2D rotation from body to world frame.

Teleporting — Writing the New State to the Simulator

EVENTS.PY 
    asset.write_root_pose_to_sim(
        torch.cat([final_pos, quats], dim=-1),
        env_ids=env_ids
    )
    asset.write_root_velocity_to_sim(velocities, env_ids=env_ids)
PLAIN ENGLISH

torch.cat([final_pos, quats], dim=-1) — concatenates the position (3 values) and quaternion (4 values) into a single (num_resets × 7) tensor. Isaac Lab's write_root_pose_to_sim expects this exact format: $[x, y, z, q_w, q_x, q_y, q_z]$.

write_root_pose_to_sim — this is a teleport. It doesn't smoothly move the car; it instantly sets the root link's position and orientation in the physics engine. The env_ids argument ensures we only modify the specified environments.

write_root_velocity_to_sim — similarly teleports the velocity. Sets both linear and angular velocity of the root body. Currently everything is zero (dead stop), but the infrastructure supports rolling starts.

Together, these two calls fully define the car's rigid-body state at spawn: where it is, which way it faces, and how fast it's moving.

Zeroing Joint States on Reset

EVENTS.PY 
    joint_pos = asset.data.default_joint_pos[env_ids]
    joint_vel = torch.zeros_like(asset.data.joint_vel[env_ids])
    asset.write_joint_state_to_sim(joint_pos, joint_vel, env_ids=env_ids)
PLAIN ENGLISH

default_joint_pos — the default joint positions from the URDF/USD asset definition. For the Ackermann car, this means: wheels at neutral rotation, steering at zero angle. We reset the joints to their "factory default" configuration.

joint_vel = zeros_like — zero out all joint velocities. No wheel spin, no steering rate. The car is completely still internally.

write_joint_state_to_sim — writes both joint positions and velocities to the physics engine in one call. Like the root pose teleport, this is an instant state override — it doesn't go through the physics solver.

This is important because the car might have been spinning its wheels wildly or had its steering cranked to the limit when it died. Without zeroing the joints, those residual states would carry over into the new episode.

🔧
The Three Levels of Reset

A complete reset touches three independent state groups:

1. Root pose — where the chassis is in the world (position + orientation)

2. Root velocity — how fast the chassis is moving (linear + angular)

3. Joint states — the internal configuration of wheels and steering (positions + velocities)

Missing any of these would leave "ghost state" from the previous episode — a common source of subtle bugs in RL environments.

Resetting the Distance Accumulator

EVENTS.PY 
    if "distance" in env.extras:
        env.extras["distance"][env_ids] = 0.0
PLAIN ENGLISH

env.extras["distance"] — the running odometer that tracks how far each car has traveled along the centerline during the current episode. This is used by the reward function (distance progress reward) and for logging.

[env_ids] = 0.0 — zero out the distance for every environment being reset. The new episode starts with zero distance traveled.

The if guard handles the edge case where the distance key hasn't been created yet (e.g., during the very first simulation step before any reward computation has run).

Resetting the GoSignalManager FSM

EVENTS.PY 
    try:
        from mdp.go_signal_manager import get_go_signal_manager
        mgr = get_go_signal_manager(num_envs=env.num_envs, device=env.device)
        mgr.reset(env_ids)
    except Exception:
        pass
PLAIN ENGLISH

get_go_signal_manager — retrieves the singleton GoSignalManager instance. This is the FSM (Finite State Machine) that controls the traffic-light countdown: RED → YELLOW → GREEN → GO.

mgr.reset(env_ids) — resets the FSM for the specified environments back to its initial state (RED, timer = 0). This ensures the new episode starts with a fresh countdown sequence.

try/except — a defensive pattern. If the GoSignalManager module doesn't exist or hasn't been configured, the reset silently continues without it. This makes the spawn function work even in simplified training setups that don't use the go-signal system.

Without this reset, the FSM would carry over its state from the dead episode — the new episode might start in GREEN or mid-countdown, which would be incorrect.

Complete Function — All Together

EVENTS.PY — FULL FUNCTION 
def reset_robot_to_fixed_spawn(env, env_ids, asset_cfg=SceneEntityCfg("robot")):
    asset = env.scene[asset_cfg.name]
    num_resets = len(env_ids)

    # ── Fixed spawn coordinates (track-local frame) ──
    base_spawn_x, base_spawn_y = -16.197, 5.50
    base_spawn_yaw = 1.5708  # π/2 — facing +Y

    # ── Domain randomization slots (all disabled) ──
    rand_offset_x = torch.zeros(num_resets, device=env.device)
    rand_yaw      = torch.zeros(num_resets, device=env.device)
    rand_vel_x    = torch.zeros(num_resets, device=env.device)

    # ── Build world-space spawn positions ──
    env_origins = env.scene.env_origins[env_ids]
    final_pos = torch.zeros((num_resets, 3), device=env.device)
    final_pos[:, 0] = env_origins[:, 0] + base_spawn_x + rand_offset_x
    final_pos[:, 1] = env_origins[:, 1] + base_spawn_y
    final_pos[:, 2] = env_origins[:, 2] + 0.12  # safe drop height

    # ── Raycast + quaternion per environment ──
    quats = torch.zeros((num_resets, 4), device=env.device)
    query = omni.physx.get_physx_scene_query_interface()
    for i, env_id in enumerate(env_ids):
        world_x, world_y = final_pos[i, 0].item(), final_pos[i, 1].item()
        hit = query.raycast_closest((world_x, world_y, 100.0), (0.0, 0.0, -1.0), 200.0)
        yaw_offset = rand_yaw[i].item()
        half_yaw = (base_spawn_yaw + yaw_offset) / 2.0
        quats[i, 0] = math.cos(half_yaw)  # w
        quats[i, 1] = 0.0                # x
        quats[i, 2] = 0.0                # y
        quats[i, 3] = math.sin(half_yaw)  # z
        if hit["hit"]:
            final_pos[i, 2] = hit["position"][2] + 0.12

    # ── Initial velocity (world frame) ──
    velocities = torch.zeros((num_resets, 6), device=env.device)
    velocities[:, 0] = rand_vel_x * torch.cos(base_spawn_yaw + rand_yaw)
    velocities[:, 1] = rand_vel_x * torch.sin(base_spawn_yaw + rand_yaw)

    # ── Teleport ──
    asset.write_root_pose_to_sim(torch.cat([final_pos, quats], dim=-1), env_ids=env_ids)
    asset.write_root_velocity_to_sim(velocities, env_ids=env_ids)

    # ── Zero joints ──
    joint_pos = asset.data.default_joint_pos[env_ids]
    joint_vel = torch.zeros_like(asset.data.joint_vel[env_ids])
    asset.write_joint_state_to_sim(joint_pos, joint_vel, env_ids=env_ids)

    # ── Reset distance odometer ──
    if "distance" in env.extras:
        env.extras["distance"][env_ids] = 0.0

    # ── Reset GoSignalManager FSM ──
    try:
        from mdp.go_signal_manager import get_go_signal_manager
        mgr = get_go_signal_manager(num_envs=env.num_envs, device=env.device)
        mgr.reset(env_ids)
    except Exception:
        pass
PLAIN ENGLISH — EXECUTION FLOW

Step 1: Pick the fixed spawn point (-16.197, 5.50) with heading π/2 (facing +Y). Domain randomization slots exist but are all zeroed.

Step 2: Convert to world coordinates by adding the per-environment origin offsets. Set Z to a safe 12cm above origin as a fallback.

Step 3: For each environment, fire a PhysX ray straight down to find the actual road height, and build a yaw quaternion using the half-angle formula.

Step 4: Compute world-frame velocity from the forward speed and heading (currently zero).

Step 5: Teleport the car — write the new pose and velocity to the simulator.

Step 6: Reset joints to factory defaults with zero velocity.

Step 7: Zero the distance odometer so the new episode starts fresh.

Step 8: Reset the GoSignalManager FSM back to RED so the traffic light countdown restarts.

🏗️
Design Philosophy: Ready for Curriculum Learning

This function is deliberately over-engineered for what it currently does (spawn at a single fixed point). The three randomization slots — position, heading, velocity — are the exact levers you'd pull in a curriculum learning setup:

Level 1 (current): Fixed spawn, no randomization. The policy learns the basic task.

Level 2: Add small position offsets (±30 cm). The policy learns to handle starting slightly off-center.

Level 3: Add heading noise (±5°). The policy learns to correct initial misalignment.

Level 4: Add initial velocity (0.5–2.0 m/s). The policy learns to handle rolling starts.

Each level increases difficulty gradually, preventing catastrophic forgetting while building robustness.
