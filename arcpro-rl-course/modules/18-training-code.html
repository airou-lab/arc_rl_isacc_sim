Part 7: The Training Pipeline

Launching Training (Code)

A line-by-line dissection of train_skrl.py — the script that wires everything together and starts the learning loop

Everything we've built so far — the environment, the reward function, the actor and critic networks — has been a collection of individual pieces sitting on a workbench. This file is the assembly manual. train_skrl.py takes every component, wires them into a single executable pipeline, and launches the reinforcement learning loop. It's deceptively short (~80 lines of meaningful code), but every line carries architectural significance. Let's walk through every class, every method, every constant.

1 — The Compatibility Problem

Our environment outputs observations as a Python dictionary with keys like "telemetry" and "tiled_camera". This is a perfectly natural representation — different sensor modalities live in different arrays. But SKRL's RandomMemory (the experience replay buffer) doesn't support gym.spaces.Dict observation spaces. It expects a single flat tensor it can store row-by-row. This is a common friction point when combining Isaac Lab environments with external RL libraries.

🔌
The Wrapper Pattern in RL

Rather than modifying the environment or the library, we insert a wrapper — a thin adapter class that sits between the environment and the agent. The environment still outputs dicts internally; the wrapper intercepts those dicts, processes them, and presents a flat tensor to the agent. This is the classic Adapter Pattern from software engineering, and it's everywhere in RL codebases. Isaac Lab itself uses this pattern (the IsaacLabWrapper we saw earlier), and now we add our own on top.

SKRLFlattenWrapper does two things: (1) it runs camera images through a frozen ResNet-18 to produce a 512-dimensional feature vector, and (2) it concatenates that vector with the 12-dimensional telemetry to produce a single flat observation of shape (524,). If cameras are disabled, it simply passes through the 12-dimensional telemetry unchanged.

2 — SKRLFlattenWrapper: Constructor

TRAIN_SKRL.PY — SKRLFlattenWrapper.__init__ 
class SKRLFlattenWrapper(Wrapper):
    def __init__(self, env):
        super().__init__(env)
        if self._env.cfg.enable_cameras:
            self.resnet = resnet18(weights=ResNet18_Weights.IMAGENET1K_V1).to("cuda:0")
            self.resnet.eval()
            for param in self.resnet.parameters():
                param.requires_grad = False
            self.resnet.fc = nn.Identity()
            self.mean = torch.tensor([0.485, 0.456, 0.406]).view(1, 3, 1, 1).to("cuda:0")
            self.std = torch.tensor([0.229, 0.224, 0.225]).view(1, 3, 1, 1).to("cuda:0")
PLAIN ENGLISH

Line 1: We inherit from SKRL's Wrapper base class, which handles method delegation — any method we don't override gets forwarded to the wrapped environment.

Line 3: Call the parent constructor, which stores the wrapped environment as self._env.

Line 4: Check the environment config. If cameras aren't enabled, we skip all the vision machinery entirely — no ResNet, no normalization tensors, no GPU memory wasted.

Line 5: Load a ResNet-18 pretrained on ImageNet (1.28M images, 1000 classes). The IMAGENET1K_V1 weights give us a network that already understands edges, textures, shapes, and objects. We move it to GPU immediately.

Line 6: Set the network to evaluation mode. This disables dropout and switches BatchNorm layers to use running statistics instead of batch statistics. Critical — without this, the feature extraction would be noisy and non-deterministic.

Lines 7-8: Freeze every parameter. We iterate through all ~11.7M parameters and set requires_grad = False. This means PyTorch won't compute gradients for ResNet during backpropagation — it's a fixed feature extractor, not a learnable component. This saves enormous amounts of GPU memory and compute.

Line 9: Replace the final classification layer with Identity. The original ResNet-18 ends with a fully-connected layer that maps 512 features → 1000 class logits. We don't want classification — we want the raw 512-dimensional feature vector that precedes that layer. Replacing fc with nn.Identity() means the network now outputs a 512-dim vector instead of 1000 class probabilities.

Lines 10-11: Store the ImageNet normalization constants as tensors shaped (1, 3, 1, 1) for broadcasting across batch and spatial dimensions. These are the per-channel means and standard deviations computed across the entire ImageNet dataset.

🧠
Why ResNet-18 Specifically?

ResNet-18 is the smallest member of the ResNet family — just 11.7M parameters compared to ResNet-50's 25.6M or ResNet-152's 60.2M. For a frozen feature extractor running inside a tight RL loop, this matters enormously. The forward pass must execute for every single environment step across all parallel environments. ResNet-18 provides a good balance: the 512-dimensional feature vector is rich enough to encode lane markings, road boundaries, and obstacles, while being fast enough to not bottleneck the simulation.

🏗️
The nn.Identity() Trick — Decapitating a Classifier

This is a widely-used pattern in transfer learning. A standard image classifier has the structure: backbone → avgpool → fc(512→1000). The backbone extracts features, average pooling reduces spatial dimensions, and the final FC layer maps to class probabilities. By replacing fc with nn.Identity(), we "decapitate" the classifier. The network now outputs the 512-dimensional vector that was the input to the classification head — a compact, semantically rich representation of the image content. This is sometimes called a "feature backbone" or "encoder."

3 — ImageNet Normalization: The Sacred Constants

The normalization constants deserve special attention because getting them wrong silently destroys your feature extraction — the network will produce garbage features without any error message.

🔴

Red Channel

mean = 0.485, std = 0.229
ImageNet images tend to have moderate red content. The relatively small std means red values are fairly consistent across the dataset.

🟢

Green Channel

mean = 0.456, std = 0.224
Slightly lower mean than red. Natural images (grass, trees, foliage) contribute heavily to ImageNet, but green values are balanced by indoor and urban scenes.

🔵

Blue Channel

mean = 0.406, std = 0.225
The lowest mean — blue is the least dominant channel in typical photographs. Sky regions contribute blue, but they're often a small portion of each image.

The normalization formula applied per-pixel is:

$x_{\text{normalized}} = \frac{x - \mu_c}{\sigma_c}$

where $c \in \{R, G, B\}$. This transforms pixel values from the range $[0, 1]$ to approximately $[-2.1, 2.6]$, centering each channel around zero with unit-ish variance. The pretrained ResNet's BatchNorm layers and learned weights expect inputs in this distribution — they were trained on data normalized this way. Feed in raw $[0, 255]$ pixel values and the network's internal activations will be completely off-scale.

The tensors are shaped (1, 3, 1, 1) — that's (batch=1, channels=3, height=1, width=1). PyTorch's broadcasting rules mean this will automatically expand across any batch size and any spatial resolution. A batch of 64 images at 240×320 resolution gets normalized in a single vectorized operation with no loops.

4 — The _flatten_obs Method: From Dict to Flat Tensor

TRAIN_SKRL.PY — _flatten_obs 
def _flatten_obs(self, obs):
    vec = obs["telemetry"]
    if "tiled_camera" in obs:
        img = obs["tiled_camera"].float()
        if img.dim() == 4 and img.shape[-1] == 3:
            img = img.permute(0, 3, 1, 2)
        if img.max() > 1.0:
            img = img / 255.0
        img = (img - self.mean) / self.std
        with torch.no_grad():
            visual_feats = self.resnet(img)
        return torch.cat([visual_feats, vec], dim=1)
    return vec
PLAIN ENGLISH

Line 2: Extract the telemetry vector — always present regardless of camera mode. This is a tensor of shape (num_envs, 12) containing speed, heading error, lateral offset, distances to lane boundaries, etc.

Line 3: Check if camera data exists in the observation dict. If cameras are disabled, this key won't be present and we skip straight to returning raw telemetry.

Line 4: Cast image data to float32. Isaac Lab's tiled camera may return uint8 (0-255) or float16. We need float32 for the normalization math and for ResNet's BatchNorm layers.

Lines 5-6: The NHWC → NCHW permutation. Isaac Lab outputs images in NHWC format (Batch, Height, Width, Channels) — this is the format used by most rendering engines and image libraries. But PyTorch's convolutional layers expect NCHW (Batch, Channels, Height, Width). The permute(0, 3, 1, 2) rearranges axes: batch stays at 0, channels move from position 3 to position 1, and spatial dims shift right. A (64, 240, 320, 3) tensor becomes (64, 3, 240, 320).

Lines 7-8: Defensive normalization to [0, 1]. If pixel values are in the 0-255 range (uint8 style), divide by 255. If they're already in [0, 1], this is a no-op. This handles both cases gracefully.

Line 9: Apply ImageNet normalization. Each channel is centered and scaled: $x_c' = (x_c - \mu_c) / \sigma_c$. After this, pixel values are roughly in the range $[-2.1, +2.6]$ — exactly what the pretrained ResNet expects.

Lines 10-11: Run the frozen ResNet in a no_grad context. Even though we froze the parameters, torch.no_grad() provides an additional optimization: it tells PyTorch not to build a computation graph for this forward pass at all, saving memory for intermediate activations. The output is a tensor of shape (num_envs, 512) — 512 features per image.

Line 12: Concatenate vision features with telemetry. torch.cat([visual_feats, vec], dim=1) joins (N, 512) and (N, 12) along the feature dimension to produce (N, 524). This single flat vector is what the policy and value networks receive.

Line 13: Fallback path — if no camera data exists, just return the raw 12-dim telemetry vector. This makes the wrapper work seamlessly in both camera-on and camera-off modes.

📐
The 524-Dimensional Observation Vector

When cameras are enabled, the final observation is a 524-dimensional vector:

  • Dimensions 0–511 (512 values): Visual features from ResNet-18. These encode high-level image semantics — lane markings, road curvature, obstacle positions, horizon line, etc. — compressed from a 240×320×3 = 230,400 pixel image down to just 512 numbers.
  • Dimensions 512–523 (12 values): Telemetry — speed, heading, lateral offset, lane distances, and other vehicle state measurements.

This fusion strategy is called early fusion (or "feature-level fusion"): we combine modalities before they enter the policy network, letting the policy's MLP learn cross-modal correlations. The alternative would be late fusion, where each modality has its own processing branch and outputs are combined at the decision layer. Early fusion is simpler and works well when one modality (vision) has already been processed into a compact representation.

5 — The observation_space Property

TRAIN_SKRL.PY — observation_space 
@property
def observation_space(self):
    shape_dim = 524 if self._env.cfg.enable_cameras else 12
    return gym.spaces.Box(low=-np.inf, high=np.inf, shape=(shape_dim,))
PLAIN ENGLISH

Lines 1-2: This is a property, not a regular method — it's accessed as env.observation_space without parentheses. It overrides whatever the wrapped environment reports as its observation space.

Line 3: Choose the dimensionality based on camera mode. With cameras: 512 (ResNet) + 12 (telemetry) = 524. Without cameras: just 12 (telemetry only).

Line 4: Return a continuous Box space with infinite bounds. The (-inf, inf) range is standard for RL — it tells SKRL "these are unbounded real numbers" which is correct since ImageNet-normalized features and telemetry values can be any float. The shape (shape_dim,) is a 1D tuple, making this a flat vector space — exactly what SKRL's RandomMemory needs.

This property is critical for the downstream pipeline. When SKRL's memory buffer allocates storage, it reads env.observation_space.shape to determine how many columns each row needs. When the actor and critic networks are constructed, they read this space to determine their input layer size. If this property returned the original Dict space (or the wrong dimensionality), everything downstream would break.

6 — Data Flow Through the Wrapper

Let's trace exactly what happens when the environment produces one observation:

1️⃣

Environment Output

{"telemetry": (N, 12), "tiled_camera": (N, 240, 320, 3)}
A dict with a float32 telemetry tensor and a uint8 image tensor in NHWC layout.

2️⃣

Cast & Permute

Image → float32 → permute to (N, 3, 240, 320) NCHW layout → divide by 255 → values now in $[0, 1]$.

3️⃣

ImageNet Normalize

$(x - \mu) / \sigma$ per channel → values now in $[\approx\!\!-2.1, \approx\!\!+2.6]$. ResNet's BatchNorm layers expect this distribution.

4️⃣

ResNet Forward

Frozen ResNet-18 (no grad): (N, 3, 240, 320) → conv layers → avgpool → Identity (was fc) → (N, 512). 230,400 pixels compressed to 512 features.

5️⃣

Concatenate

torch.cat([visual_feats, telemetry], dim=1) → (N, 524). A single flat tensor ready for the policy network.

7 — TelemetryPPO: Custom Telemetry Logging

SKRL's built-in PPO class tracks standard RL metrics — rewards, episode lengths, policy loss, value loss. But for autonomous driving, we care about domain-specific metrics: How fast is the car going? How far is it from the lane boundaries? The TelemetryPPO class extends PPO with custom logging for these driving-specific signals.

TRAIN_SKRL.PY — TelemetryPPO 
class TelemetryPPO(PPO):
    def record_transition(self, states, actions, rewards,
                          next_states, terminated, truncated,
                          infos, timestep, timesteps):
        super().record_transition(states, actions, rewards,
                                  next_states, terminated, truncated,
                                  infos, timestep, timesteps)
        speed = 0.0
        if "speed_mps" in infos:
            speed = infos["speed_mps"].mean().item()
            self.track_data("Telemetry / Speed_MPS", speed)
        self._print_counter += states.shape[0] if states is not None else 1
        if self._print_counter >= 10000:
            print(f"Step {timestep} | Rew: {self._last_ep_rew:.1f} | Len: {self._last_ep_len:.0f} | Spd: {speed:.2f}")
            self._print_counter = 0
PLAIN ENGLISH

Line 1: TelemetryPPO inherits from SKRL's PPO class. We only override one method — record_transition — keeping all the actual PPO algorithm logic (advantage estimation, policy updates, clipping) untouched.

Lines 2-7: Override record_transition, which SKRL calls after every environment step to store the $(s, a, r, s', \text{done})$ tuple. The first thing we do is call super().record_transition() so all of SKRL's internal bookkeeping still happens — storing data in the memory buffer, updating episode counters, etc.

Line 8: Initialize speed to 0.0 as a safe default in case the info dict doesn't contain speed data.

Lines 9-11: If the environment's infos dict contains "speed_mps" (speed in meters per second), extract the mean across all parallel environments using .mean().item(). The .item() converts a single-element tensor to a Python float. Then log it to SKRL's tracking system via track_data(), which feeds into TensorBoard / Weights & Biases.

Line 12: Increment the print counter by the batch size (number of parallel environments). With 64 envs, each call to record_transition adds 64 to the counter. This means the counter tracks total environment interactions, not training steps.

Lines 13-15: Every 10,000 environment interactions, print a human-readable status line to the console. This gives a quick "pulse check" without needing TensorBoard: current timestep, last episode reward, last episode length, and current mean speed. Then reset the counter to 0.

📊
Why 10,000 Steps Between Prints?

With 64 parallel environments, 10,000 interactions happen every ~156 calls to record_transition. At ~500 FPS simulation speed, that's about every 20 seconds of wall-clock time. Frequent enough to monitor progress, sparse enough to not flood the terminal. The counter uses states.shape[0] (the batch dimension) to correctly account for the number of parallel environments — if you run with 128 envs instead of 64, you get prints at the same real-time frequency because more interactions happen per step.

🔗
The record_transition Hook Point

record_transition is the ideal place for custom logging because it's called at every single environment step with the complete transition data. It has access to states, actions, rewards, next_states, termination flags, and importantly the infos dict — which is where the environment passes auxiliary data like speed and lane distances. Other override points (like _update) only fire during training updates, which happen less frequently.

8 — main() — Environment Construction

The main() function is where the entire training pipeline is assembled. Let's walk through it in three parts: environment setup, model creation, and training launch.

TRAIN_SKRL.PY — main() Part 1: Environment 
def main():

    env_cfg.scene.num_envs = args_cli.num_envs
    env_cfg.enable_cameras = args_cli.enable_cameras

PLAIN ENGLISH

Line 2: Create the environment configuration object. ARCProEnvCfg contains all the defaults — reward weights, track geometry, physics timestep, sensor configurations. This is the giant config class we studied in earlier modules.

Line 3: Override the number of parallel environments from the command line. The default might be 64, but you might pass --num_envs 128 for faster data collection or --num_envs 4 for debugging. This directly controls how many copies of the car + track are simulated simultaneously.

Line 4: Set the camera flag from the command line. When True, the environment will include a tiled camera sensor and the wrapper will load ResNet-18. When False, the agent trains on telemetry only — much faster but vision-blind.

Line 5: Manually call __post_init__(). In a normal dataclass flow, __post_init__ runs automatically after __init__. But since we modified fields after construction (lines 3-4), we need to re-run it so dependent calculations (like observation space dimensions) are recomputed with the updated values.

Line 6: Create the actual Isaac Lab environment. ManagerBasedRLEnv is Isaac Lab's main environment class. It takes our config and spins up the full simulation: USD scene loading, physics engine (PhysX), sensor pipelines, reward/termination managers — everything. After this line, the simulation is live.

Line 7: Wrap with IsaacLabWrapper. This is SKRL's official adapter for Isaac Lab environments. It translates between Isaac Lab's API (which uses .step() with dictionaries of observation groups) and SKRL's expected Gym-like API. Crucially, it also extracts the critic observation group — if the config defines separate observation groups for actor and critic (Asymmetric Actor-Critic), this wrapper makes the critic's observations available via env.state_space.

Line 8: Wrap with our SKRLFlattenWrapper. This is the wrapper we just studied — it flattens the dict observations into a single tensor, optionally running images through frozen ResNet-18. After this line, the environment presents a standard Box(524,) or Box(12,) observation space to the agent.

🪆
The Wrapper Stack: Three Layers Deep

The environment is now wrapped three layers deep, like Russian nesting dolls:

  1. Innermost: ManagerBasedRLEnv — the raw Isaac Lab simulation with dict observations and manager-based architecture.
  2. Middle: IsaacLabWrapper — SKRL's adapter that translates the API and extracts critic observations for AAC.
  3. Outermost: SKRLFlattenWrapper — our custom adapter that flattens dicts into tensors and runs vision encoding.

When the agent calls env.step(action), the call propagates inward through all three layers. When observations come back, they propagate outward — being transformed at each layer. This is entirely standard in modern RL. OpenAI Gym's entire design is built around wrapper composition.

9 — main() — Memory Buffer

TRAIN_SKRL.PY — main() Part 2: Memory 
    memory = RandomMemory(memory_size=128, num_envs=env.num_envs, device="cuda:0")
PLAIN ENGLISH

Create a rollout buffer with 128 steps of storage per environment. In on-policy algorithms like PPO, the "memory" isn't really a replay buffer — it's a rollout buffer. It stores the last 128 steps of experience from each parallel environment. After 128 steps, PPO uses all this data for a training update, then discards it and starts collecting fresh data.

The total number of transitions stored is 128 × num_envs. With 64 environments, that's 8,192 transitions per training update. With 128 environments, it's 16,384. This is the "rollouts" parameter — we'll see it again in the PPO config.

The device="cuda:0" means the buffer lives on GPU. Since both the environment and the networks are on GPU, keeping the buffer there too avoids any CPU↔GPU data transfers during training.

📦
Why memory_size=128?

The memory_size must match the rollouts parameter in the PPO config (which we'll see is also 128). This value determines how many steps of experience PPO collects before performing a training update. 128 steps is a moderate rollout length — long enough to capture multi-step dynamics (the car needs several steps to complete a turn) but short enough to keep training updates frequent. With 64 parallel environments × 128 steps = 8,192 total transitions per update batch, which is a healthy batch size for PPO.

10 — main() — Model Creation

TRAIN_SKRL.PY — main() Part 3: Models 
    models = {}
    models["policy"] = ARCProActor(env.observation_space, env.action_space, "cuda:0")
    state_space = getattr(env, "state_space", env.observation_space)
    models["value"] = ARCProCritic(state_space, env.action_space, "cuda:0")
PLAIN ENGLISH

Line 1: Create an empty dictionary to hold the models. SKRL expects a dict with specific keys: "policy" for the actor (action-producing network) and "value" for the critic (value-estimating network).

Line 2: Create the actor (policy) network. ARCProActor is the custom Gaussian MLP we built in earlier modules. It receives env.observation_space — which, thanks to our wrapper, is Box(524,) with cameras or Box(12,) without. It receives env.action_space — which is Box(2,) for [throttle/brake, steering]. The network is placed on "cuda:0".

Line 3: Attempt to get the critic's state space for Asymmetric Actor-Critic (AAC). getattr(env, "state_space", env.observation_space) tries to access env.state_space. If the IsaacLabWrapper detected a separate "critic" observation group in the environment config, it will have set state_space to the critic's (potentially richer) observation space. If no separate critic group exists, getattr falls back to env.observation_space — meaning actor and critic see the same observations.

Line 4: Create the critic (value) network. ARCProCritic receives state_space — which may be different from the actor's observation space if AAC is enabled. The critic might see privileged information (like exact centerline distance or perfect lane positions) that the actor doesn't have access to. This is the essence of Asymmetric Actor-Critic: train the critic with rich data, but the actor only gets what a real car would have.

🎭
The getattr Trick for AAC

The line getattr(env, "state_space", env.observation_space) is a clean pattern for optional AAC support. Here's how it works in practice:

  • If AAC is configured: The environment config defines two observation groups — "policy" (actor sees cameras + limited telemetry) and "critic" (critic sees full privileged state). IsaacLabWrapper exposes the critic group via env.state_space. The critic gets richer input than the actor.
  • If AAC is not configured: Only one observation group exists. state_space attribute doesn't exist on the wrapper. getattr falls back to env.observation_space. Actor and critic receive identical observations. Standard PPO.

This single line of code makes the entire script compatible with both standard PPO and asymmetric PPO, with zero conditional logic.

11 — main() — PPO Configuration

TRAIN_SKRL.PY — main() Part 4: PPO Config 
    cfg_ppo = PPO_DEFAULT_CONFIG.copy()
    cfg_ppo["rollouts"] = 128
    cfg_ppo["mini_batches"] = 16
    cfg_ppo["learning_rate"] = 1e-4
PLAIN ENGLISH

Line 1: Start from SKRL's default PPO configuration and make a copy. The defaults include sensible values for clip ratio (0.2), entropy coefficient, discount factor (0.99), GAE lambda (0.95), number of PPO epochs, and many other hyperparameters. We only override the three parameters that are most task-specific.

Line 2: rollouts = 128 — Collect 128 environment steps before performing a training update. This must match the memory_size we set earlier. With 64 parallel environments, each training update uses 128 × 64 = 8,192 transitions. Longer rollouts capture more temporal context (good for driving where maneuvers span many steps) but delay learning updates.

Line 3: mini_batches = 16 — Split the rollout data into 16 mini-batches for each PPO epoch. With 8,192 total transitions, each mini-batch contains 8,192 ÷ 16 = 512 transitions. Smaller mini-batches mean more gradient updates per epoch (more learning) but noisier gradients. 16 is a moderate choice.

Line 4: learning_rate = 1e-4 — Set the Adam optimizer's learning rate to 0.0001. This is on the conservative side for PPO (typical range is 1e-4 to 3e-4). A lower learning rate means slower but more stable learning — appropriate for a complex continuous control task where aggressive updates could cause the policy to suddenly forget how to drive.

🧮
The Math of Rollouts, Mini-Batches, and Epochs

Let's trace the exact data flow for one PPO training cycle (assuming 64 envs):

  1. Collection phase: Run the environment for 128 steps across 64 envs → 8,192 transitions stored in the rollout buffer.
  2. For each PPO epoch (default is ~8 epochs per update):
    • Shuffle the 8,192 transitions randomly.
    • Split into 16 mini-batches of 512 transitions each.
    • For each mini-batch: compute advantages, policy ratio, clipped loss, value loss → one gradient update.
  3. That's 16 gradient updates per epoch × ~8 epochs = ~128 gradient updates per collection cycle.
  4. Clear the buffer, go back to step 1.

This is why PPO is "on-policy but sample-efficient" — it reuses each batch of experience across multiple epochs, unlike vanilla policy gradient which uses each transition exactly once.

TRAIN_SKRL.PY — main() Part 5: Launch

PLAIN ENGLISH

Lines 1-8: Create the PPO agent. TelemetryPPO (our custom subclass) receives everything it needs:

• models: The dict containing "policy" (ARCProActor) and "value" (ARCProCritic). SKRL will use the policy to sample actions and the value function to compute advantages.

• memory: The 128-step rollout buffer where transitions are stored before training updates.

• cfg: The PPO hyperparameters — rollout length, mini-batch count, learning rate, plus all the defaults we didn't override (clip ratio, GAE lambda, entropy coeff, etc.).

• observation_space and action_space: These tell SKRL the shapes of inputs and outputs. SKRL uses these internally for initialization and validation.

• device="cuda:0": Everything runs on the first GPU.

Lines 9-13: Create the trainer. SKRL's SequentialTrainer orchestrates the training loop. Its only config is timesteps — the total number of environment interactions before training ends. This comes from the command line (e.g., --total_timesteps 1000000). The trainer also receives the wrapped environment and the agent.

Line 14: trainer.train() — This is where the magic happens. This single call enters a loop that runs for the specified number of timesteps. Each iteration: (1) the agent queries the policy for actions, (2) the environment steps forward, (3) transitions are stored in memory, (4) every 128 steps, PPO runs its training update. This call blocks until training is complete — it could run for hours or days depending on the timestep budget.

14 — Key Design Decisions in This File

1️⃣
Frozen ResNet vs. Trainable CNN

A frozen pretrained ResNet-18 is used instead of training a CNN from scratch. This is a deliberate tradeoff: we sacrifice the ability to learn task-specific visual features (like "what a lane marking looks like in our specific simulation") in exchange for massive computational savings and stable gradients. Training a CNN end-to-end through RL is notoriously difficult — the reward signal is sparse and delayed, making it hard for gradients to propagate back through dozens of convolutional layers. A frozen ResNet provides a "good enough" visual representation from day one, letting the MLP policy focus on learning the driving behavior rather than simultaneously learning to see and drive.

2️⃣
Wrapper Composition Over Monolithic Design

The file stacks three wrappers rather than building a single "mega-environment" that handles everything. This modularity means you can swap components independently: use a different RL library (just replace the outer wrapper), use a different visual encoder (just replace the ResNet code in SKRLFlattenWrapper), or use a different simulation (just replace the inner environment). Each layer has exactly one job.

3️⃣
Camera-Optional Architecture

The entire vision pipeline is gated behind enable_cameras. This isn't just a convenience feature — it fundamentally changes the training workflow. Camera-free training (telemetry only) runs 3-5× faster because it skips rendering, image transfer, and ResNet forward passes. The recommended workflow is: first train a competent telemetry-only policy (fast iteration, quick experiments), then enable cameras and fine-tune (or retrain) with visual input. The observation space automatically adapts (12 vs. 524 dimensions), and all downstream code works unchanged.

4️⃣
Everything on GPU

Notice that every component is explicitly placed on "cuda:0" — the ResNet, the normalization tensors, the memory buffer, the actor, the critic, and the agent. Isaac Lab's simulation also runs on GPU via PhysX. This means the entire pipeline — from physics simulation to observation processing to neural network inference to gradient updates — runs entirely on the GPU without any CPU↔GPU data transfers. This is critical for performance: a single GPU-to-CPU transfer per step would halve the throughput.

"Deep Residual Learning for Image Recognition" Kaiming He, Xiangyu Zhang, Shaoqing Ren, Jian Sun (2015)

The paper that introduced ResNet. The core insight — skip connections that allow gradients to flow through identity mappings — enabled training networks with 100+ layers. ResNet-18, the smallest variant used here as a frozen feature extractor, has 8 residual blocks with 2 convolutional layers each, producing a 512-dimensional feature vector after global average pooling.

"Proximal Policy Optimization Algorithms" John Schulman, Filip Wolski, Prafulla Dhariwal, Alec Radford, Oleg Klimov (2017)

The PPO algorithm implemented by SKRL and configured in this file. The key hyperparameters we set — rollout length (128), mini-batch count (16), and learning rate (1e-4) — directly interact with PPO's clipped surrogate objective. The clip ratio (default 0.2) limits how far the new policy can deviate from the old policy in a single update, and mini-batch SGD over multiple epochs extracts maximum learning from each batch of experience.
